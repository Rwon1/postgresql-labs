# Работа 8: измерения

PostgreSQL 16.10. Замеры сделаны на одной базе после ANALYZE. Время относится к отдельному запуску; оно зависит от кэша и нагрузки.

В seed исправлена скобка в выражении `unit_price`; формула цены сохранена.

## Три эксперимента

| План | Scan | Estimated / actual rows (Scan) | Loops | Buffers hit / read (корень) | Execution, ms |
|---|---|---|---|---|---:|
| B1. До индекса | Seq Scan | 119 / 120 | 1 | 1270 / 0 | 37.182 |
| B1. После индекса — тот же SQL | Index Scan | 119 / 20 | 1 | 23 / 3 | 1.704 |
| B2. До индекса | Seq Scan | 1171 / 1500 | 1 | 1264 / 0 | 20.755 |
| B2. После индекса — тот же SQL | Bitmap Heap Scan, Bitmap Index Scan | 1171 / 1500; 1171 / 1500 | 1; 1 | 1264 / 3 | 5.756 |
| B3. До индекса | Seq Scan | 100 / 80 | 3 | 4000 / 0 | 155.019 |
| B3. После индекса — тот же SQL | Bitmap Heap Scan, Bitmap Index Scan | 239 / 240; 239 / 240 | 1; 1 | 243 / 3 | 1.55 |

1. Индекс `(customer_id, order_date DESC, order_id DESC)` позволяет читать историю клиента в нужном порядке и остановиться после 20 строк. Проверены COUNT и сумма ID до/после.
2. Частичный индекс по дате хранит только cancelled-заказы. Проверены COUNT и сумма ID за один и тот же период.
3. Индекс `order_items(product_id)` находит позиции конкретного товара. Число позиций, количество единиц и выручка до/после совпали.

Оставлены эти три индекса: каждый связан с отдельным проверенным запросом. Полные планы приложены файлами `*_plan.txt` и `*_plan.json`.

Actual rows указаны на один проход: в параллельном плане B3 80 × 3 = 240 строк. В B1 индексное чтение остановлено LIMIT после 20 строк. В B2 число блоков таблицы осталось тем же: выигрыш этого запуска нельзя объяснять сокращением чтения всех блоков.

## Остальные сравнения

`paid` и `completed` составляют 85% заказов. Для чтения столь большой части таблицы последовательное сканирование может стоить дешевле. Тестовый индекс `status` удалён; его размер записан в CSV.
Переписывание даты диапазоном само по себе не создаёт индекс. В эксперименте D1 набор индексов одинаковый. Полные результаты обеих форм сравнены через `EXCEPT ALL` в обе стороны: различий нет.
При выборе двух полей вместо `SELECT *` уменьшилась ширина строки плана; ID и даты совпали. Это проверка одного и того же списка заказов, но не тождественности всех столбцов.
`ORDER BY order_date DESC, order_id DESC LIMIT 20` выбирает последние 20 заказов однозначно. Сверка с ROW_NUMBER не нашла различий.

OFFSET 50000 и keyset с готовым курсором вернули одинаковые 20 строк (`40.csv`). Здесь нет отдельного индекса для глобального порядка по дате: оба плана читают таблицу. OFFSET использовал внешнюю сортировку с временными блоками, keyset — отбор по курсору и top-N. Стоимость получения курсора не входит в замер keyset; в приложении его передают с предыдущей страницы.

Справка: [EXPLAIN в PostgreSQL 16](https://www.postgresql.org/docs/16/using-explain.html).
